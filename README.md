# Antifraud Social Demo

Synthetic social-network relying-party demonstration. The preliminary portal
shows how a person reviews, authorizes, rejects and
verifies a request to sign an immutable publication manifest without exposing
private wallet material to React or to the relying party.

Start future work by reading
[`docs/USE_CASE_TASKS.md`](docs/USE_CASE_TASKS.md) and
[`.codex/skills/build-antifraud-social-demo/SKILL.md`](.codex/skills/build-antifraud-social-demo/SKILL.md),
then use the separately maintained Antifraud Data Space MVP Prompt v10 as the
complete implementation contract.

## Boundary

- This is a synthetic relying party, not a production social network.
- Authentication does not authorize a signature.
- A click, publication, delivery or read state is not a signature.
- React never creates or receives a seed, PIN, biometric value or private key.
- The BFF must reuse the reviewed high-level SDK and managed-wallet behavior.
- Demo is the only executable MVP environment. Test Network is disabled until
  the project owner supplies Kubernetes and configuration; Production is
  disabled.
- C2PA interoperability is a versioned adapter boundary; it is not proof that
  media content is true or was not generated by AI.
- Antifraud documents are Schema.org `DigitalDocument`/`MediaObject` records,
  never FHIR `DocumentReference` resources. PDF, spreadsheet, Word, image,
  video and other governed bytes travel only in DIDComm `attachments[]`.
- Age-over evidence already belongs to the controller-to-employee evidence
  journey. A relying party may request the existing predicate but never
  derives or stores a duplicate.

## Current status

Preliminary UI plus a local BFF and in-memory Fabric demo adapter. The demo
creates a server-owned immutable-manifest digest, supports authorization and
rejection, records a simulated receipt and reloads it through the BFF. The
receipt explicitly carries `cryptographicProof: false` and is not a wallet
signature, Fabric transaction, local-network result or Test Network result.

Demo retains the same interface, options, components, validation and business
flows designed for future Test Network use. It uses the normal BFF, high-level
SDK and gateway contracts, but its Fabric boundary is the six-second in-memory
simulation. BFF and gateway reuse their configured collection-prefix resolver;
React never selects a prefix, and Demo cannot access disabled Test Network or
Production namespaces.

For Firebase App Hosting, the project owner—not Bolt—authorizes the official
Firebase GitHub application and chooses the Firebase project, region, backend
and live branch. Never paste or commit a service-account key. Runtime Firebase
Admin/Firestore uses Application Default Credentials, and Secret Manager names
may be referenced from `apphosting.yaml`. Prefer Firestore for the hosted Demo;
PostgreSQL plus local IPFS is the verified self-hosted profile. Supabase is
currently a blob adapter and MongoDB is not wired as the current vault
repository, so neither is claimed as a complete database profile.

Enabling Google alone is not enough for local or hosted login. Register the
social Firebase web app, authorize `localhost` and every deployed Beta origin,
provide only public browser configuration, verify the ID token in the BFF and
preserve popup-compatible headers. Follow the exact
[Beta Firebase authentication handoff](docs/BETA_FIREBASE_AUTH.md). Google
authenticates only the relying-party session; it grants no signature or person
index access.

Run with Node.js 24:

```bash
npm ci
ANTIFRAUD_SOCIAL_DEMO_MODE=true npm run dev
```

The synthetic demo PIN is `0426`. It is a public fixture and never represents
production authentication or wallet protection.
